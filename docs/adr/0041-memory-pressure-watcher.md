# ADR-0041: 메모리 압박 감시는 상주 프로세스 없이 리드 세션의 triflux mod 가 직접 한다

## 컨텍스트와 문제 (Context)

ADR-0040 으로 워커 실행 위치 판단은 리드 몫이 됐지만, 측정 시점이 "디스패치 직전" 한 번이라 리드가 작업 중일 때 압박이 2(warn) 나 4(critical) 로 올라가도 알지 못한다. 사용자는 Stats 앱이 보여 주는 것과 같은 커널 값 `kern.memorystatus_vm_pressure_level` 을 리드 밖 상주 감시기가 1초마다 읽고, 단계가 바뀔 때만 리드에게 알리는 방식을 골랐다. Codex 가 Stats 3.0.21 을 역분석한 결과 Stats 도 이 sysctl 을 1초 폴링하며 압박 이벤트는 구독하지 않는다.

전달 수단으로 처음 제시된 것은 리드 세션의 inbox 소켓(`/tmp/cc-socks/<pid>.sock`)이었다. 공식 문서는 소켓 경로와 인증 줄까지만 공개하고 메시지 본문 형식은 공개하지 않는다. 리드 세션 자신의 소켓에 평문 한 줄과 JSON 한 줄을 넣어 봤지만 어느 쪽도 도착하지 않았다. 외부 데몬은 세션의 자식이 아니라서 리드가 bypassPermissions 모드면 승인 대기에 걸리고, 리드 소켓 경로가 세션마다 바뀌어 감시기가 리드를 찾는 방법도 따로 필요했다.

상주 감시기 자체도 다시 봤다. 신호의 소비자는 리드뿐이라 리드가 없을 때 측정해도 대응할 주체가 없고, Node 상주 프로세스는 기본 30~50MB 를 차지하며 장기간 돌 때 누수 위험이 있다. 메모리 압박을 보려고 메모리를 상시 쓰는 셈이다.

## 결정 (Decision)

- 상주 프로세스, LaunchAgent, 상태 파일을 두지 않는다. 감시는 triflux mods(`mods/triflux`) 의 훅 모듈이 리드 세션 안에서 직접 한다.
- 리드 등록은 세션 안 `/tfx-lead on|off|status` 슬래시 명령이다. on 이면 `$.clock.every` 로 2초마다 `$.process.run(['sysctl','-n','kern.memorystatus_vm_pressure_level'])` 을 읽고, off 면 타이머를 멈춘다. 등록은 `$.store` 에 세션 ID 로 남겨 모듈이 다시 로드돼도 이어진다. 리드가 아닌 세션은 측정하지 않는다.
- 1, 2, 4 만 유효로 본다. 첫 유효 표본은 기준으로만 저장한다. 다른 유효 단계가 새 표본 두 번 연속 같을 때 확정하고 상승과 하강을 같은 규칙으로 다룬다. 표본 간격이 5초를 넘으면(수면, 멈춤) 후보를 버리고 새 두 표본으로 다시 확정한다. 읽기 실패와 유효하지 않은 값도 후보를 끊는다.
- 확정한 전이는 `$.prompt.submit` 으로 턴을 연다. `$.prompt.submit` 은 세션이 쉴 때 턴을 열므로, 앞선 제출이 아직 턴을 열지 못했으면 새 전이를 따로 제출하지 않고 그 턴이 시작된 뒤 확정 단계가 달라져 있으면 한 번 더 제출한다. 리드가 긴 턴 중이면 전이 여러 개가 마지막 상태 하나로 합쳐진다. 본문은 이전 단계, 현재 단계, 시각, `skills/tfx-lead/SKILL.md` "압박 변화 대응" 절을 따르라는 한 줄, 그 사이 또 바뀌었을 수 있으니 `/tfx-lead status` 로 확인하라는 한 줄이다. 같은 단계 지속에는 턴을 열지 않는다.
- `/clear` 뒤에는 같은 프로세스가 새 세션 ID 로 이어지므로 mod 가 등록 키를 새 ID 로 옮겨 감시를 이어 간다. 세션이 끝나면(`/clear` 제외) 그 세션의 등록 키를 지운다. resume 한 세션은 다시 `/tfx-lead on` 해야 한다. `/tfx-lead status` 는 등록 여부, 마지막 표본의 단계와 시각을 보여 준다.
- 단계별 대응 규칙은 `skills/tfx-lead/SKILL.md` 의 "압박 변화 대응" 절이 정본이다. 기준값은 `.claude/rules/tfx-routing.md` 그대로다. macOS 만 지원하고 다른 OS 에서는 `/tfx-lead on` 이 지원하지 않는다고 답한다.

## 검토한 대안 (Considered Options)

- **inbox 소켓 직접 전송**: 데몬이 리드 소켓에 한 줄을 쓴다. 본문 형식이 비공개라 바이너리 조사가 필요하고 Claude Code 업데이트마다 깨질 수 있다. 외부 송신자는 bypass 리드에서 승인 대기에 걸리고, 리드 소켓을 찾는 레지스트리가 또 필요하다. 기각.
- **Channels(MCP)**: 공식 푸시 경로지만 research preview 이고 claude.ai 또는 API 키 인증과 `--channels` 플래그가 필요하다. 감시기 하나를 위해 세션 시작 방식을 바꾸게 된다. 기각, 안정화되면 재검토.

- **launchd 상주 Node 가 상태 파일을 쓰고 mod 가 파일을 폴링**: 처음 택했던 안. 리드가 없을 때도 기록이 남고 다른 프로세스가 상태를 읽을 수 있다. 그러나 소비자가 리드뿐이라 그 기록을 쓸 곳이 없고, 상주 Node 가 30~50MB 를 상시 차지한다. 사용자가 상주 프로세스의 램 사용과 누수를 우려해 기각.
- **작은 Swift/C 상주 바이너리 + RSS 상한**: Codex 역분석 권고. 발자국은 작지만 빌드 도구와 서명이 필요하고 저장소의 Node 테스트 체계 밖이다. 상주 자체가 필요 없어진 뒤로는 이점이 없어 기각.

## 결과 (Consequences)

- 추가 프로세스와 설치 단계가 없다. 리드가 `/tfx-lead on` 만 하면 단계 전이를 턴으로 받는다. 확정까지 최대 4초(2초 폴링 두 표본)이고, 턴은 리드가 쉴 때 열리므로 긴 턴 중의 전이는 그 턴이 끝난 뒤 마지막 상태로 합쳐져 도착한다.
- 2초마다 sysctl 프로세스를 하나 띄운다. 리드 세션 하나에서만 돌아 비용은 무시할 수준이다.
- 리드가 없으면 아무도 측정하지 않는다. 디스패치 직전 측정(ADR-0040) 은 그대로 유지한다.
- 리드가 둘 이상 등록돼 있으면 둘 다 깨어난다. 리드 교대 때 `/tfx-lead off` 를 빠뜨리면 옛 리드도 깨어나므로 점검표에 넣는다.
- 되돌릴 조건: 리드 없는 시간대의 압박 이력이 필요해지면 상태 파일 기록을 다시 검토한다. Claude Code 가 외부 프로세스용 inbox 쓰기 형식이나 안정된 Channels 를 공개하면 외부 감시기 안을 다시 볼 수 있다.
